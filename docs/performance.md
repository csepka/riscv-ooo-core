# Measured performance

Generated by `python3 scripts/report.py` from the JSON reports produced by
`python3 scripts/benchmark.py`. All workloads are independently checked at retirement.
These are simulation measurements with a synthetic memory model, not silicon results.

## Measurement conditions

* Icarus Verilog 12; reset PC zero; RV32IM; single dispatch and retirement.
* Main matrix: instruction responder delay 8 cycles; data delay 30 plus 0–15
  cycles from a seeded per-transaction generator, plus ready/valid interface edges.
* Request readiness has seeded cycle-based backpressure. Configurations see the
  same per-transaction data delays; changed request timing can change stall exposure.
* Caches: 16 direct-mapped one-word lines each for instructions and data; cold reset.
* Cycles include startup and final trap reporting. IPC excludes the terminating
  EBREAK/trap; `retirement_events` includes it. CPI is cycles / successful retirements.
* The baseline is the sequential RTL built in this repository. No historical
  three-stage or commercial-CPU baseline is asserted.

## Interpretation and next priorities

The frontend bubble removal helps ALU and divide-overlap workloads. Memory-heavy
workloads can regress slightly because cycle-based backpressure and recovery
alignment change. Small caches help repeated loop/read locality but cold streams
and conflicts can pay lookup overhead without enough hits. The static predictor
mispredicts most taken loop branches. Larger ROB capacity alone cannot remove
head-only memory serialization or single-request fetch limits.

The next measured candidates are a better branch predictor with an explicit
recovery design, a buffered fetch interface, and an independently verified LSQ
allowing safe loads before head. Dual-wide rename is deferred until those
bottlenecks and physical timing have evidence-based solutions.
